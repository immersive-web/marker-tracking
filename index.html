Abstract

The WebXR Marker Tracking Module expands the WebXR Device API with functionality to detect, decode and spatially track supported physical markers in the user’s environment.

1. Introduction

This module expands the WebXR Device API with a mechanism for detecting supported physical markers in the user’s environment, decoding marker data and tracking a marker’s spatial pose. The initial version of this module focuses on QR code markers. Unlike the WebXR Image Tracking proposal, which is designed for image targets supplied by the application when requesting an XR session, marker tracking is intended to support physical markers discovered during an active XR session. Marker detection, decoding and tracking are performed by the XR device and user agent. The application receives constrained marker tracking results, rather than raw camera images. These results are intended to allow an application to associate decoded marker data with a marker’s pose and use that pose to place or update virtual content in the user’s environment.

2. Discovery Model

2.1. Marker

A marker symbology identifies the machine-readable marker format used by a physical marker. QR Code is the initial marker symbology supported by this version of the module.

A marker is a physical, machine-readable visual target of a supported marker symbology.

A tracked marker corresponds to the information used by the XR device to detect, decode and spatially track one physical instance of a marker during an XRSession.

A tracked marker represents a physical instance, rather than only its decoded data. Two physically distinct markers that encode identical data may be represented as distinct tracked markers when the XR device can distinguish them.

Each tracked marker has an associated:

  1. marker symbology;

  2. marker tracking state;

  3. marker space;

  4. decoded marker payload, where available;

  5. marker extent, where available;

  6. marker identifier; and

  7. XRMarker object.

2.2. QR code markers

This first version of the module defines QR codes as its initial supported marker symbology. A QR code is a two-dimensional matrix barcode that can store various types of data. A user agent determines whether a physical QR code is supported and suitable for detection and tracking. This module defines an initial Web-facing representation for decoded QR code payload data through the payloadString attribute on XRMarker. That representation specifies how decoded text is exposed to Web applications. Future versions may expose byte-oriented payload data. It does not define the application-specific meaning, safety, language, directionality or interpretation of that data. A user agent may be unable to detect or track QR codes whose physical presentation is unsuitable for reliable detection, including codes with insufficient contrast, visual modifications, embedded imagery, altered modules or other customisation. Non-normative author guidance for marker presentation may be provided separately. Future versions of this module may define and support additional marker symbologies. Such additions must not change the behaviour of QR code markers defined by this version.

2.3. Marker tracking state

A tracked marker has an associated marker tracking state. The marker tracking state describes whether the XR device is actively observing the marker, or is reporting a pose derived from a previous observation. The possible marker tracking states are:

"untracked"
The XR device has no current tracking information for the marker.
"tracked"
The marker is currently being actively tracked by the XR device. The marker is at least partially visible to a tracking camera or otherwise actively observed by the tracking system.
"emulated"
The marker was previously tracked during the current XR session, but its current pose is based on a previous observation rather than active observation of the physical marker.

The "untracked" state is an internal tracking state and is not exposed through XRMarkerTrackingResult.

An "emulated" result indicates that the application should not assume that the reported pose still corresponds to the marker’s current physical location. For a marker that is expected to remain stationary, such as one attached to a wall or fixed sign, the previous pose may remain useful while active observation is temporarily unavailable.

For a marker that may have moved since it was last observed, the emulated pose may be stale. Applications that require accurate physical alignment should consider hiding, fading, de-emphasising or otherwise indicating uncertainty in marker-relative content until the marker returns to the "tracked" state.

When active tracking resumes, applications should account for the possibility that the marker pose may be corrected to a different position or orientation.

The marker tracking state describes whether the physical marker itself is currently being actively observed by the marker-tracking system. This is distinct from emulatedPosition, which describes whether the computation of an XRPose between two XRSpace objects relies on an emulated position. An application’s pose query may therefore have emulation characteristics that are separate from whether the marker itself is actively being observed.

2.4. Marker space and geometry

A tracked marker has an associated marker space, which is a device XRSpace representing the tracking system’s 6DoF pose of the marker in the user’s environment. The origin of a marker space is the centre of the marker’s physical bounds. The marker’s front face lies in the x-y plane of the marker space:

  • the positive x-axis points towards the marker’s right edge;

  • the positive y-axis points towards the marker’s top edge; and

  • the positive z-axis is orthogonal to the marker plane and points towards the viewer when the marker’s front face is visible.

A marker space is used with getPose() to obtain the marker’s pose relative to another XRSpace. The tracking system may provide either an actively tracked pose or an emulated pose, as indicated by the marker tracking state. A tracked marker may have an associated marker extent. A marker extent describes the physical width and height of the marker in metres, measured in the x-y plane of the marker space. The marker extent information is optional and may be estimated by the XR device. The marker extent information represents the physical bounds of the detected marker, not its pixel dimensions. Applications must not assume that an available extent is exact.

2.5. Decoded marker data

A tracked marker may have an associated decoded marker payload. The decoded marker payload is the data obtained by the XR device upon detection of the physical marker. The decoded marker payload is opaque to this module. It may represent text, a URL, a product identifier, a serial number, application-specific or custom data. This module does not define the semantics, safety, language, directionality or interpretation of decoded marker payloads. A tracked marker may still be spatially tracked even when decoded marker payload data is unavailable or empty.

In this initial version, decoded marker payload data is exposed to applications through the payloadString attribute on XRMarker. The payloadString attribute is `null` when decoded marker payload data is unavailable or cannot be represented as a string.

Future versions of this module may expose a byte-oriented representation for decoded marker payloads.

2.6. Marker identity and session scope

A tracked marker has an associated marker identifier. A marker identifier is an internal identifier used by the user agent to associate observations of a tracked marker during the XRSession in which it was detected. The marker identifier is not exposed to applications. Each tracked marker has an associated XRMarker object. For as long as a tracked marker remains associated with an XRSession, the user agent MUST use the same XRMarker object to represent that tracked marker. Applications can therefore use XRMarker object identity to correlate observations of the same tracked marker across XR frames, including comparing objects for equality or using an XRMarker as a map key. Marker identity is scoped to the XRSession. User agents must not imply that an XRMarker object or internal marker identifier represents persistent recognition of the same physical marker across XR sessions. If a marker stops being tracked and is later detected again, the user agent may associate it with the same tracked marker only when it can determine that it represents the same physical marker instance. Otherwise, the user agent may treat it as a new tracked marker with a new XRMarker object. Applications must not use decoded marker payload data as a substitute for marker identity. Multiple physical markers may encode identical payloads.

3. WebXR Device API Integration

This module expands the definitions of XRSessionInit, XRSession, and XRFrame.

3.1. XRSessionInit

3.1.1. `marker-tracking` feature descriptor

This module introduces the string marker-tracking as a new valid feature descriptor for use in the requiredFeatures or optionalFeatures sequences when requesting an `immersive-ar` session. The marker-tracking feature descriptor applies only to `immersive-ar` sessions. A user agent MUST NOT grant the feature to `inline` or `immersive-vr` sessions. Marker tracking is restricted to `immersive-ar` sessions because it exposes the spatial relationship between supported physical markers and the user’s real environment. An XR device is capable of supporting the marker-tracking feature if it can detect, decode and spatially track supported QR code markers in the user’s physical environment.

3.1.2. Capability and configuration options

This version of the module does not add any additional members to XRSessionInit. An application requests marker tracking by including the marker-tracking feature descriptor in requiredFeatures or optionalFeatures. Individual physical markers are discovered during the XR session. The application does not provide a list of marker targets when requesting the session.

3.1.3. Set up marker tracking

In order to set up marker tracking for a requestSession() session request, add the following steps to initialize the session for the new XRSession session:

  1. Set session’s list of tracked markers to an empty list.

  2. If `marker-tracking` is not contained in session’s set of granted features, abort these steps.

  3. Initialise any XR device or user agent resources required to detect, decode and track supported markers.

  4. Append the update tracked markers algorithm to session’s list of frame updates.

3.2. XRSession

3.2.1. Marker-tracking session state

Each XRSession has a list of tracked markers, which is a list of tracked marker detected during that session. The list is initially empty. A tracked marker is added to the list when the XR device first reports a supported physical marker. A tracked marker remains associated with the session while the user agent needs to report its tracking state or pose. A user agent MAY stop retaining a tracked marker once it is no longer tracked and no longer needed to report an emulated pose. If the same physical marker is detected again, the user agent MAY associate it with the existing tracked marker only when it can determine that it represents the same physical marker instance.

3.2.2. Capability reporting

This version of the module does not define a Web exposed capability-reporting method or attribute on XRSession.

3.3. XRFrame

3.3.1. Update tracked markers

In order to update tracked markers for an XRFrame frame, the user agent MUST run the following steps:

  1. Let session be frame’s session object.

  2. Let observations be the set of supported physical marker observations reported by the XR device for frame.

  3. For each tracked marker marker in session’s list of tracked markers, set marker’s marker tracking state to `"untracked"`.

  4. For each observation in observations:

  5. Let marker be the tracked marker associated with observation, if one exists.

  6. If marker does not exist:

    1. Create a new tracked marker marker, with its decoded marker payload and marker extent initially unavailable.

    2. Set marker’s marker symbology from observation.

    3. Assign marker a marker identifier.

    4. Create a new XRSpace with its session set to session, its native origin tracking marker’s physical pose according to the coordinate system defined in § 2.4 Marker space and geometry, and its origin offset set to the identity transform. Set marker’s marker space to this space.

    5. Create a new XRMarker xrMarker and associate it with marker.

    6. Set marker’s associated XRMarker object to xrMarker.

    7. Append marker to session’s list of tracked markers.

  7. Set marker’s marker tracking state to `"tracked"` if the XR device is actively tracking the physical marker. Otherwise, set marker’s marker tracking state to `"emulated"` if the XR device provides a pose derived from a previous observation.

  8. Update the native origin of marker’s marker space based on the XR device’s estimate of the marker’s pose, without replacing the XRSpace object.

  9. If observation provides decoded marker payload data, update marker’s decoded marker payload from observation. Otherwise, retain its existing value.

  10. If observation provides marker extent information, update marker’s marker extent from observation. Otherwise, retain its existing value.

3.3.2. XRMarkerTrackingState

The XRMarkerTrackingState enum represents a tracked marker’s marker tracking state.

enum XRMarkerTrackingState {
    "tracked",
    "emulated",
};

The XRMarkerTrackingState values correspond to the marker tracking state values defined in the Discovery Model. The "untracked" marker tracking state is an internal state used by the algorithms in this module and is not exposed through XRMarkerTrackingState. Marker-tracking results are returned only for markers whose state is `"tracked"` or `"emulated"`.

3.3.3. XRMarkerExtent

An XRMarkerExtent represents the physical dimensions of a detected marker in meters.

[SecureContext, Exposed=Window]
interface XRMarkerExtent {
    readonly attribute float widthInMeters;
    readonly attribute float heightInMeters;
};

The widthInMeters attribute represents the physical width of the marker in meters, measured along the x-axis of the marker space.

The heightInMeters attribute represents the physical height of the marker in meters, measured along the y-axis of the marker space.

An XRMarkerExtent represents the physical bounds of the detected marker, not its pixel dimensions. Applications must not assume that the reported dimensions are exact.

3.3.4. XRMarker

An XRMarker represents one physical marker tracked by the XR device during an XRSession.

[SecureContext, Exposed=Window]
interface XRMarker {
    [SameObject] readonly attribute XRSpace markerSpace;
    readonly attribute DOMString? payloadString;
    readonly attribute XRMarkerExtent? extent;
};

For as long as the corresponding tracked marker remains associated with the session, the same XRMarker object MUST be used to represent it.

The markerSpace getter steps are to return the marker space of the tracked marker associated with this XRMarker. The same XRSpace object is returned for the lifetime of the XRMarker.

The payloadString getter steps are:

  1. Let marker be the tracked marker associated with this XRMarker.

  2. If marker’s decoded marker payload is unavailable or cannot be represented as a string, return `null`.

  3. Return the string representation of marker’s decoded marker payload.

The extent getter steps are:

  1. Let marker be the tracked marker associated with this XRMarker.

  2. If marker’s marker extent is unavailable, return `null`.

  3. Let extent be a new XRMarkerExtent.

  4. Set extent’s widthInMeters to the width of marker’s marker extent.

  5. Set extent’s heightInMeters to the height of marker’s marker extent.

  6. Return extent.

3.3.5. XRMarkerTrackingResult

An XRMarkerTrackingResult represents the current tracking result for a tracked marker during an XRFrame.

[SecureContext, Exposed=Window]
interface XRMarkerTrackingResult {
    [SameObject] readonly attribute XRMarker marker;
    readonly attribute XRMarkerTrackingState trackingState;
};

The marker attribute identifies the XRMarker associated with this result. Results for the same tracked marker across multiple XR frames MUST reference the same XRMarker object while that marker remains associated with the XRSession.

The trackingState attribute represents the marker tracking state recorded when this XRMarkerTrackingResult was created for its corresponding XRFrame. Its value does not change when the marker’s tracking state is updated in subsequent frames.

The initial version of this module does not expose marker symbology or an explicit marker identifier. Future versions may add marker-specific attributes to XRMarker, such as marker symbology, byte-oriented payload data or more detailed marker geometry, or add frame-specific information to XRMarkerTrackingResult where needed.

3.3.6. Obtain marker-tracking results

The XRFrame interface is expanded with a getMarkerTrackingResults() method.

partial interface XRFrame {
    FrozenArray<XRMarkerTrackingResult> getMarkerTrackingResults();
};

The getMarkerTrackingResults() method steps are:

  1. Let frame be this XRFrame.

  2. If frame’s active boolean is `false`, throw an InvalidStateError exception.

  3. Return the result of running the obtain marker-tracking results algorithm for frame.

In order to obtain marker-tracking results for an XRFrame frame, the user agent MUST run the following steps:

  1. Let session be frame’s session object.

  2. Let results be an empty list.

  3. For each tracked marker marker in session’s list of tracked markers:

    1. If marker’s marker tracking state is `"untracked"`, continue to the next entry.

    2. Let result be a new XRMarkerTrackingResult.

    3. Set result’s marker to marker’s associated XRMarker object.

    4. Set result’s trackingState to marker’s marker tracking state.

    5. Append result to results.

  4. Return a new `FrozenArray` containing the elements of results.

Marker-tracking results only contain information about markers whose marker tracking state is `"tracked"` or `"emulated"`. A marker-tracking result is specific to the frame in which it is obtained. Applications MUST NOT rely on XRMarkerTrackingResult object identity to correlate results across XR frames. Applications can instead use the result’s marker attribute to identify the tracked marker. Results for the same tracked marker reference the same XRMarker object while that marker remains associated with the XRSession. Applications can use `result.marker.markerSpace` with getPose() to obtain the marker’s pose relative to another XRSpace.

4. Comfort and Presentation Considerations

Marker tracking is not intended to provide frame-perfect object tracking. Applications SHOULD account for tracking-state changes, pose updates and possible discontinuities when attaching virtual content to a marker. In particular, when a marker result is `"emulated"`, applications should consider whether the physical marker may have moved since it was last actively observed. For markers expected to remain stationary, continuing to present marker-relative content using the emulated pose may be appropriate. For markers that may move, applications should avoid presenting marker-relative content as though its physical alignment were still known. Depending on the experience, applications may hide, fade or otherwise indicate uncertainty in that content until active tracking resumes. Applications should also account for a possible pose correction when a marker transitions from `"emulated"` back to `"tracked"`.

5. Security and Privacy Considerations

5.1. Sensitive marker information

Marker tracking exposes information derived from the user’s physical environment. Sensitive marker information includes, but is not limited to:

  • Presence of supported physical markers in the user’s environment;

  • A marker’s spatial pose or approximate physical location;

  • Marker extent, size or other geometry where available;

  • Decoded marker payload data, such as URLs, identifiers, serial numbers or application-specific data; and

  • Changes in marker tracking state over time.

Decoded marker payloads are data observed from markers in the user’s physical environment. They may themselves be sensitive, regardless of whether they describe the user’s environment or not. For example, a marker may encode a product identifier, location identifier, account related value, URL or other application specific content. Marker payloads MUST be treated as untrusted input. User agents MUST NOT automatically navigate to, make a network request to, or otherwise act on decoded marker data solely as part of marker detection or tracking. Applications are responsible for safely handling decoded payload data, particularly before navigating, making network requests or using it in security-sensitive contexts. Marker tracking provides a narrower privacy surface than raw camera access because it does not expose camera frames to the application. This does not make marker tracking non-sensitive: marker presence, pose and decoded payload data can still reveal information about the user and their surroundings.

5.2. Feature gating and user awareness

Marker tracking is a sensitive WebXR capability and MUST be requested using the marker-tracking feature descriptor. This version of the module restricts marker tracking to `immersive-ar` sessions. Because marker tracking is available only to immersive-ar sessions, it operates within the WebXR Device API’s existing spatial-tracking permission and user-intent framework, including the `xr-spatial-tracking` Permissions Policy. This module must additionally define whether the marker-tracking feature requires explicit user consent, whether it needs a separate policy-controlled feature, and whether decoded marker payloads require different treatment from pose-only marker tracking. A user agent MUST ensure that there is a clear signal of user intent before enabling marker tracking. The mechanism used to establish user intent, including any permission prompt or other user-facing explanation, is left to the user agent. The user agent SHOULD make it clear that enabling marker tracking may allow the application to receive information about supported physical markers in the user’s environment, including decoded marker data where exposed by this module. This version of the module treats spatial marker information and decoded marker data as part of the same `marker-tracking` capability. A future version may define more granular controls if there is an interoperable need to distinguish pose-only marker tracking from access to decoded marker data.

5.3. Limiting unnecessary environmental disclosure

User agents SHOULD limit unnecessary disclosure of marker information. For example, a user agent may wait until a marker is prominently visible in the user’s central view before first reporting it to an application. Once the marker has been detected, the user agent may continue to report its pose when it becomes partially occluded or less prominent, subject to the marker’s tracking state. For initial detection, a user agent SHOULD consider whether the marker is sufficiently prominent in the user’s central field of view or camera view to indicate that the user is intentionally scanning it. User agents SHOULD avoid initiating marker tracking for markers that are only briefly visible, distant, too small to be clearly noticed or visible only in peripheral vision. The detailed criteria used for initial detection are implementation-defined and may vary according to the device, tracking system and marker symbology. User agents MAY limit the number of simultaneously reported markers, reduce the precision of marker geometry, or throttle marker-result updates where necessary to mitigate privacy or fingerprinting risks. Such mitigations MUST NOT introduce tracking behaviour that is likely to cause user discomfort.

5.4. Session scope and persistence

Marker identifiers, tracking state, marker spaces and decoded marker data are scoped to the XRSession in which they are reported. This module does not define a mechanism for correlating a marker observed in one XR session with a marker observed in a later XR session, unless such behaviour is explicitly defined by a future version of this module. When an XR session ends, the user agent MUST stop exposing marker-tracking results for that session. This does not prevent an application from explicitly storing decoded marker data using existing Web Platform storage mechanisms, subject to the normal privacy and security expectations of those mechanisms.

6. Accessibility Considerations

Marker tracking can support accessible immersive experiences. For example, a detected marker may help an application identify a physical object, retrieve accessible information about it or place virtual guidance relative to it. This module does not define accessibility requirements for QR codes, barcodes, GS1 identifiers or other marker symbologies. It does not alter the existing requirements, guidance or deployment practices associated with those machine-readable formats and specifications. Instead, it adds spatial detection and tracking capabilities around supported markers within an XR session. Marker scanning can create barriers where it is the only way to access information or complete an action. Applications should provide an equivalent non-marker path where appropriate, particularly for critical actions and for users who may have difficulty locating, seeing, aiming at or physically approaching a marker. When an application or content author controls the presentation of a physical marker, it should:

  • Provide readable text or other accessible instructions explaining the marker’s purpose and how to use it.

  • Avoid relying on colour alone in the instructions or surrounding visual cues used to identify, distinguish or explain a marker.

  • Use sufficient contrast between the marker and its background;

  • Place the marker where it can reasonably be seen, reached or approached by the intended users;

  • Ensure that the marker is large enough to be detected at its intended viewing distance;

  • Follow the relevant presentation and deployment guidance for supported marker symbologies; and

  • Avoid making marker scanning the only available path for important information, authentication or task completion.

Applications should expose decoded marker information, marker status and related actions through accessible user-interface mechanisms, including HTML UI where possible. For example, an application that displays a virtual overlay after detecting a marker should also provide an accessible textual status or control through its HTML interface.

7. Internationalization Considerations

This module does not define QR code or other barcode symbologies, GS1 identifiers or GS1 Digital Link syntax or the application specific semantics of decoded payload data. Different marker symbologies and application ecosystems can define their own encoding and payload rules. For example, a GS1 Digital Link payload can associate a machine-readable product identifier with online information. This module does not interpret or modify those rules; it only provides a potential mechanism for associating supported marker data with an XR spatial pose. After decoding according to the applicable marker symbology, user agents should return textual payload data without additional case conversion, Unicode normalisation, locale-dependent transformation or inferred language or text direction. The initial version exposes decoded marker data through payloadString. The normative payload-processing algorithm still needs to define character encoding, error handling behaviour, treatment of non-text payloads and whether future byte-oriented payload access is needed. QR codes are the initial focus of this module because they provide a practical cross-platform starting point. This does not imply that QR codes are the only globally relevant marker format. Future versions may consider other barcode symbologies or marker families where platform support and use cases justify them.

Document conventions

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.
